TD-PPagop-26082303 reasoned that `dashboard`'s `unless-stopped` restart
policy "retries that failure indefinitely, at Docker's capped backoff of
roughly one attempt a minute" once its `tailscale` sidecar has stopped and
the network namespace `dashboard` shares with it can no longer be joined.
That record is `status: resolved`, and `TECH-DEBT.md`'s "Resolution and
history" keeps a resolved item's body in place rather than editing it, so
this item records the correction rather than changing that file.

A live run against `main` @ `412b025` (VM1, 2026-08-23/24, corroborated on a
keyless node), posted in full on issue #728 and summarised on issue #706,
measured `dashboard` under both `restart: on-failure:5` (the policy PR #704
added) and the anchor's `unless-stopped`, across two configurations: the
sidecar killed while `dashboard` was already running (the namespace outlives
the sidecar container; `dashboard` keeps running indefinitely, unaffected by
either policy), and the sidecar already down when `dashboard` tried to start
(zero restart attempts under **both** policies, held 180 s).

The mechanism TD-PPagop-26082303 reasoned from does not hold: joining the
network namespace of a container that is not running is refused at *start*,
before the joining container ever runs. A container refused at start never
exits, so a restart policy keyed on exit codes — `on-failure:5` or
`unless-stopped` alike — is never consulted, and neither retries.
`dashboard` lands in `Created` with `RestartCount: 0` and exit 128 either
way; it never reaches the indefinite-retry state TD-PPagop-26082303
described under `unless-stopped`.

This does not reopen TD-PPagop-26082303 or change PR #704's disposition: the
bound it added is kept, but as a statement of intent rather than an observed
behaviour. `docs/IMPLEMENTATION-PIPELINE-SPEC.md`'s node-stack `dashboard`
entry, acceptance check 1c-v, and `deploy/docker/compose.yaml`'s `dashboard`
service comment are corrected to match, in the same pull request as this
record.
